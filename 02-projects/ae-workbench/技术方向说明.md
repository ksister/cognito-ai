## 1 产品目标与架构

工作台只做一件事：把一次技术支持变成一条可信的本地记录。飞书表、客户时间线、需求池、语雀文档都是这条记录的派生视图，不要为它们另建数据源。浏览交给 Obsidian，批量分析和写文档交给 Claude Code 直接读 markdown，工作台不重复做这些功能。

```text
微信/飞书聊天截图 → 工作台（AI 出草稿 → 黄区人工核对）→ 本地记录 markdown（截图原件 · 逐字转写 · 我的思考 · 需求线索）
                                                         ├→ 飞书表格（对外登记台账）
                                                         ├→ 客户病历本（按客户看全过程）
                                                         ├→ 需求池（每两周出需求分析）
                                                         └→ 语雀知识库（高频问题沉淀）
浏览用 Obsidian，分析用 Claude Code，都直接读本地 markdown。
```

飞书表、客户病历本、需求池、语雀文档都从同一份本地记录生成，所以录入时多花的那 1 分钟（核对和写思考）会在四个地方回本。

1. **M1 登记稳定（本轮，目标 11 月 6 日）**
   - 完成第 4 节 T1–T8，用户飞书真机验收后合入 main。
   - 上线后的成功指标（用户侧）：连续 5 个工作日，每条支持当天登记完，飞书没有重复行、没有漏附件。
2. **M2 客户病历本（11 月中）**
   - 加「接续已有问题」，一个问题从头到尾只有一条记录、一行飞书。
   - 客户页按时间线展示：每个问题的状态、截图、「我的思考」、关联需求；顶部是客户档案（行业、产线、软硬件版本、联系人）。
   - 历史飞书数据一次性导入本地：用户批准前不做（领导已把批量回填列为后置）。
3. **M3 需求池升级（11 月下旬）**
   - 需求池按「目标 → 痛点 → 方案」组织，每条需求带客户证据：哪几家、几次、原话、记录链接。用户确认后的需求写入飞书需求表（与技术支持表同一个 Base，表 ID 用环境变量 LARK\_REQ\_TABLE\_ID），一行一条聚合后的需求，不是一条支持记录一行；M1 不碰这张表。
   - 「辅助工具」类需求单独筛选，方便用户先自己做小工具验证，再推动研发改软件。
   - 同类问题出现 3 次以上时，可一键让 AI 起草语雀文档，用户修改后发布。
4. **M4 主动提醒（12 月）**
   - 每周五自动跑「体检 + 周回顾」：长期未关闭的问题、新冒出来的共性问题、本周需求线索。
   - 实现方式另定，M1–M3 稳定之前不做。

## 2 已定技术决策

以下决策已定，实现时不得违反；要改先按第 0 节规则 1 提出。

| 编号 | 决策 | 理由 | 明确不做 |
| --- | --- | --- | --- |
| D1 | 本地 markdown 是唯一事实源：`customers/<客户>/records/*.md` | Obsidian 和任何 AI 都能直接读，不被工作台绑死 | 不引入数据库做主存储；索引或缓存可以，但必须能从 md 完整重建 |
| D2 | 截图为主、文字粘贴为辅；截图走通义 VL（`DASHSCOPE_*`），文字走 `AI_*` | 用户日常输入大多是聊天截图 | 不合并两套配置；模型地址必须可配置，为换公司内部模型留口 |
| D3 | 黄区核对是保存的硬门槛 | 解决「怕 AI 理解错」 | 不提供跳过确认直接保存的路径；改动 AI 字段后必须重新确认（保留现有逻辑） |
| D4 | 先落盘本地，飞书失败不回滚，保留「复制为飞书行」降级 | 数据绝不能丢 | 飞书任何失败都不得导致本地记录丢失或回滚 |
| D5 | 飞书写入走官方 `lark-cli --as user` | 官方工具、个人身份，接入成本最低。10-30 更新：公司飞书建应用需管理员审批，审批前按 D12 执行 | 本阶段不做应用身份；`api` 模式只作备用，不扩展 |
| D6 | 「我的思考」「原始聊天记录」两节归用户所有 | 一个是原始证据，一个是用户独有判断 | AI 不得改写或删除这两节；OCR 转写保存后即视为原始记录 |
| D7 | 客户公司对不上下拉选项时写「其他-待确认」，原名并入客户/联系人 | 不污染飞书选项 | 不自动新增飞书下拉选项 |
| D8 | 不确定就留空并写入 `uncertain` | 防止编造 | 不用默认值掩盖不确定（见 T6） |
| D9 | 代码仓库保持公开，真实数据与代码分离：工作台用 KB\_DIR 指向仓库外的私有知识库目录，客户数据和真实凭据不进仓库 | 客户资料保密 | `.env.example` 只放占位符；示例数据只用虚构客户 |
| D10 | 本阶段范围冻结 | 先把登记做稳 | 自动改历史行、批量回填、客户端一键导入、飞书应用身份，全部后置 |
| D11 | 飞书字段 ID（LARK\_FIELDS）留在代码里 | 没有 Base token 和表格权限，字段 ID 无法访问任何数据；挪到配置只会增加用户的配置负担 | 不把字段 ID 挪到 .env；Base token 和表 ID 仍然只能写在 .env.local |
| D12 | 飞书写入抽象为三种通道：clipboard（复制为飞书行，默认兜底）、webhook（多维表格自动化，实测可行才启用）、cli（管理员审批后启用），由 `LARK_PUSH_MODE` 选择。所有通道都写入「本地记录ID」列，作为同一问题对应同一行的唯一键 | 建应用要管理员审批，短期拿不到；唯一键不依赖只有 API 才能拿到的飞书行号 | 不因为审批卡住 M1；webhook 地址视同密码，只放 `.env.local`；webhook 通道不传截图附件（除非实测能传） |
| D13 | 飞书技术支持表是字段的权威来源。表单字段、AI 提取字段、单选选项、复制行的列顺序，全部由一份「飞书表结构配置」驱动；配置放在 `KB_DIR` 下的 `config/feishu-table.json`，仓库只放虚构示例 | 旧的通用 11 列模板与真实表不符；表结构会变，改配置不改代码；选项里有真实客户公司名，不能进公开仓库 | 不在代码里写死字段名、选项或列顺序；不猜字段含义，含义不明的列由用户确认 |

## 3 数据模型约定

在现有记录格式（见根目录 `AGENTS.md`「技术支持记录格式」）上只做加法：新字段全部可选，旧记录不改也必须能正常读取和展示。

```yaml
# customers/<客户>/records/YYYY-MM-DD-<标题>.md 的 frontmatter，标「新增」的是本轮要加的
title: 手机中框读码率低
date: '2026-10-15'            # 聊天中最早日期
customer: 示例-深圳某3C厂
channel: 微信
contact: 王工
product: 视觉软件 V4.3
module: 读码
category: 算法效果
status: 跟进中
source: screenshot            # 新增：screenshot | paste
screenshots:                  # 新增：本记录的截图，路径相对 customers/<客户>/files/
  - 2026-10-15-手机中框读码率低-1.jpg
  - 2026-10-15-手机中框读码率低-2.jpg
feishu_synced: true
feishu_record_id: recXXXXXXXX # 新增：飞书行 id，之后更新同一行
feishu_synced_at: '2026-10-15T10:21:00+08:00'  # 新增
needs: [...]
created: ...
updated: ...
```

- **截图命名**：`<记录 date>-<标题前 20 字>-<序号>.jpg`，文件名里的非法字符替换为 `-`，重名时序号顺延。用聊天日期，不用保存日期。已有的 `截图-YYYYMMDD-N.jpg` 不改名。
- **原始聊天记录**：截图来源的记录，这一节写 VL 的逐字转写，首行固定为 `[OCR 转写，以截图为准]`，之后每行 `发言人：内容`。聊天里的时间分隔单独成行，写成 `—— 10月28日 09:12 ——`；图片、文件、语音写成 `发言人：[图片]`、`发言人：[文件] 文件名`、`发言人：[语音]`。截图不显示昵称时（微信私聊常见）按气泡位置判断：右侧是用户本人，左侧是客户。粘贴来源保持原样。
- **未关联文件**：客户 `files/` 下没被任何记录 `screenshots` 引用的文件，在客户页单独列为「未关联资料」，不隐藏、不删除。
- **M2 预留**：`followups: [{date, screenshots, summary}]` 用于「接续已有问题」，本轮只在类型定义里预留，不实现界面。
- **本地记录ID**（D12）：frontmatter 字段 `local_id`，格式 `AE-YYYYMMDD-NN`（日期取记录 date，NN 为当天两位序号）。保存记录时生成，之后永不改变，改标题、改文件名都不变。用途：复制行时写入飞书「本地记录ID」列；同一 ID 再次复制时提醒「已粘贴过」；状态变化时提示用户在飞书搜索该 ID 修改；工作台搜索框可按 ID 打开记录。旧记录在首次复制时补发 ID。

## 5 使用场景与设计目标

用户在两次技术支持之间的空档录入，任何多一步的交互都会让登记重新积压。做界面取舍时以这张表为准。

| 场景 | 用户动作 | 设计目标 |
| --- | --- | --- |
| 一次支持刚结束 | 拖入 1–9 张截图 → 核对黄区 → 写一两句思考 → 确认 | 从拖入到保存不超过 3 分钟；等 VL 时有进度提示，超时后直接引导改用粘贴 |
| 下班前 | 看有没有同步失败的记录 | 首页一屏看到全部未同步项（T5） |
| 同一问题再次跟进 | 接续已有问题（M2） | 1 分钟内追加完 |
| 每周五 | 用户用 Claude Code 直接读 md 做周回顾 | 记录格式稳定、frontmatter 可机读；工作台不做这个功能 |
| 每两周 | 需求池 → 生成需求分析 | 每条需求能追溯到具体记录文件 |

「我的思考」是需求分析唯一的高价值输入：保持输入框显眼、快捷提示可用，不要加必填或字数要求。

- [ ] 飞书需求表的全部列名、下拉选项，以及研发是否也在用这张表（M3 需要；M1 不写这张表）
