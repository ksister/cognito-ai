> 由实现 AI 维护，读者是下一个接手写代码的 AI。真实客户名、人名、ID、本机路径一律不写进本文件（放用户私有目录 `KB_DIR/交接-私有.md`）。发现与本文件不一致时，以代码和 `技术方向说明.md` 为准，并在报告里指出。

## 1 代码地图

工作台代码在 `workbench/`（Next.js 16 App Router + TypeScript，`dev` 端口 4321）。

数据流（一条记录的完整旅程）：

```text
截图/粘贴 → 记一笔(app/new + components/record-form.tsx)
  → api/extract（VL/AI 出草稿）
  → 黄区人工核对（D3 硬门槛）
  → api/records POST 保存
      ├─ lib/kb.ts createRecord → KB_DIR/customers/<客户>/records/*.md（本地唯一事实源，D1）
      ├─ lib/kb.ts saveScreenshotBatch → files/ 截图按规则命名落盘
      └─ lib/lark-bitable.ts pushRecordToFeishu → 飞书建行/更新（cli --as user，D5）
          └─ 兜底 lib/feishu.ts 生成 TSV 供「复制为飞书行」（D12）
```

- **`cursor/t15-paste-dedupe`（T15，PR #26 **已合并**到 `feat/screenshot-first-mvp`，合并提交 eb82188）**：粘贴一次出现两张图。
  - 原因（代码 + 真机都可证）：一次粘贴的 payload 里同一张图会在两个地方各列一份——`clipboardData.items`（kind=file）和 `clipboardData.files`；剪贴板图片的 `File` 是浏览器现造的（名字固定 `image.png`、`lastModified` 取创建时刻），两次拿到的不是同一个对象，旧的 `名称-大小-lastModified-类型` 去重键对不上，两张都进了截图列表。
  - 改法：新增 `lib/shot-intake.ts`。图片先统一压缩成 JPEG，再对字节求指纹（安全上下文 SHA-256，局域网 http 等非安全上下文用两个 32 位哈希兜底）；指纹相同即同一张，与文件名/大小/时间无关。`known`（已加入）和 `pending`（正在压缩哈希）两个集合一起判重，挡住两个粘贴监听同时处理同一个事件；粘贴/拖入在 `record-form.tsx` 里串行排队处理，删掉某张截图会放掉它的指纹，允许再粘一次。
  - 验证：`shot-intake.test.ts` 10 条单测（含连粘 20 次、并发两次、删后可重粘、无 crypto.subtle 兜底）；无头 Chrome 打 4321 的 `/new`，合成剪贴板事件（同一张图两个 File 对象）：**改前**一次粘贴出 2 张、连粘 20 次顶到 9 张上限；**改后**一次粘贴 1 张、连粘 20 次仍是 1 张，换一张内容不同的图正常变成 2 张。

9. **飞书按名称保留已有选项**（11-09 在测试表实测）：增删一个选项**不会**影响其他选项的颜色，也**不会**影响已有记录的客户列值。所以 v3 下「原样保留 `{hue, lightness, name}` 再追加新选项」是安全做法；实测中 42→43→42 全程原有选项颜色与 3 条记录值均不变。
10. **同一记录的飞书写入必须排队**（T11 评审 1）：保存秒回后后台写入还没写回 `feishu_record_id`，此时再保存或同步就没有行号，会建第二行。所有把记录推给飞书的入口都走 `queueSavedRecordPush`，不要直接调 `pushSavedRecord`（它不做排队）。另外 `local_id` 只在各自 KB 内唯一：换一个 KB_DIR（或同事）同一天会撞号，D18 的人员缩写就是为此。
11. **看配置、看接口返回时只输出字段名、数量和布尔值，不输出值**（11-10 教训，用户明确要求）：实现 AI 的会话内容会发到模型服务商的服务器，所以「只在自己电脑上打印、没发给别人」不等于没外传。之前为了确认 `config/feishu-table.json` 的结构和 `/api/feishu/meta` 的返回，把里面的**取值**（Base token、客户选项名）打进了会话。以后判断「配好了没有 / 有没有 fieldId / 选项有几个」，只输出：字段名、条数、true/false、以及「有值/为空」。
12. **`/api/feishu/meta` 曾把 `baseToken`、`tableId` 一起返回给浏览器**（11-10 已删，见 PR：前端从未用到这两个字段）。以后往这个接口加字段前先问：浏览器真的需要吗。`cliPath`（本机路径）目前仍会返回，属同类问题，未改。
13. **一次粘贴里同一张图会出现两次**（T15 已修，别再退回按文件名去重）：`clipboardData.items` 和 `clipboardData.files` 各列一份，剪贴板图片的 `File` 是浏览器现造的（名字固定、`lastModified` 每次都不一样），按元数据去重挡不住。判重一律走 `lib/shot-intake.ts` 的内容指纹；以后新加粘贴/拖放入口也要走 `record-form.tsx` 的 `addFiles`，别绕过去直接 `setShots`，否则又会出重复。
14. **提交信息文件必须是无 BOM 的 UTF-8**（11-10 教训）：PowerShell 5.1 的 `Out-File -Encoding utf8` 会写出 UTF-8 BOM，`git commit -F` 会把 BOM 一起写进标题（`e6edc90` 标题开头就多了一个不可见字符；用户已说不必处理，但以后别再犯）。写提交信息、PR 描述这类临时文件时用无 BOM UTF-8：编辑器直接存，或 `[System.IO.File]::WriteAllText($p, $s, [System.Text.UTF8Encoding]::new($false))`；提交后用 `git log -1 --format=%s` 看一眼标题开头。同理**不要用 PowerShell 的 `Get-Content` / `Set-Content` 去改仓库里带中文的文件**：PS 5.1 默认按 ANSI 读，会把中文写成乱码（本次改一个测试文件时踩到，只能删掉重写）；改文件一律用编辑工具，PowerShell 只用来读和跑命令。
15. **`/api/records` 的字段名是驼峰，不是 frontmatter 的下划线**（11-10 误报教训）：接口返回 `SupportRecord`，字段是 `feishuSynced` / `feishuRecordId` / `feishuSyncedAt` / `feishuAttached`；只有 md 的 frontmatter 才叫 `feishu_synced` / `feishu_record_id` / `feishu_synced_at`。我做「重启前确认无在途写入」的临时脚本时按 `feishu_synced` 读，`undefined` 被当成未同步，报出「9 条全未同步」的假异常，技术总监据此怀疑 T11 的后台写入丢了行号——实际是脚本读错键。**规则：用接口做核对前先打印键名（`Object.keys`，只打键名不打值）确认字段名；对「已同步/未同步」这类结论，再直接读 md frontmatter 复核一遍**（本次用 lark-cli 按 local_id 回查测试表 + 读 frontmatter，两种方法都是 9/9 已同步、7/9 有行号）。
16. **窗口标题只当客户线索，不当消息**（T18）：微信/飞书群标题常见「客户名(人数) 我方公司技术支持」，人数前的是客户，紧邻「技术支持」的是我方公司。私聊备注名是「标签 公司名 人名」（如「工作 宇创 张三」），要按空格/分隔符拆段：先逐段精确匹配选项/别称，精确不中再对非标签、非人名的段做相近字匹配，只取唯一命中；人名段不能当客户。私有配置把内部/我方公司放进 `customer.aiSkip` 后，标题里的简称可能只能通过 `aliases` 落到正式选项（11-09 那组就是这样命中的）；不要因为标题里出现了公司名就直接当客户，也不要把整行标题写进「原始聊天记录」。
17. **emoji 和 □ 必须在保存前清掉**（T18）：VL 会照提示词输出 emoji，旧提示词甚至要求用 □ 标看不清的字。所有截图转写都要走 `formatScreenshotChat` / `normalizeTranscriptText`，新加的展示或保存入口不要绕过去直接写 `turns[].text`，否则 md 里会留下 emoji 或 □/�。
18. **lark-cli 下载附件必须是相对路径 + 目标目录当 cwd**（T25 实测）：`+record-download-attachment --output <绝对路径>` 直接报 `unsafe output path ... --file must be a relative path within the current directory`。正确做法：`cwd` 切到目标目录，`--output .`，再用返回的 `data.downloaded[].file_token / saved_path` 对应；同一条记录里重名文件（大量 `image.png`）由 CLI 自己加序号，不要按文件名对应。通用函数已封装在 `scripts/t25-export-history.mjs` 的 `downloadRecordAttachments()`。
19. **正式表没有「本地记录ID」「需求线索」两列**（T25 实测，2026-11-10）：正式表 `tbltWWJaNx6bknQV` 共 24 列，私有配置里的 `local_id`→「本地记录id」、`needs` 在正式表都不存在；9 条本地记录与 314 条正式记录在 local_id、`feishu_record_id`（7 条指向测试表行）、问题名称+日期上都没有重合，所以历史记录**无法按本地记录ID 合并**，本地已有转写可合并 0 条。以后要让本地记录和正式表对得上，得先把「本地记录ID」列加到正式表。
20. **`KB_DIR/config/model-prices.json` 的单价必须来自用户核实**（T25 教训）：11-09 用户已在百炼控制台核实并写入——`qwen3.8-omni-flash` 输入 0.8 / 输出 2.7 元每百万 tokens，`qwen-plus` 输入 0.8 / 输出 2 元，都是最低档、可能按用量分档，来源标「百炼控制台，2026-11-09」。`qwen3-vl-plus` 仍是 null（只有切回它时才需要补）。T24 的「本月花费」按 `tokens / 1e6 × 单价` 算，不要自己编数字；换模型或调价时改这个文件并更新 `updatedAt`。
21. **脚本直接 import `src/lib/*.ts` 需要 Node ≥ 22.18**（T25）：靠 Node 的类型剥离运行，相对导入必须带 `.ts` 后缀。`workbench/package.json` 没有 `"type": "module"`，每次会打一条 `MODULE_TYPELESS_PACKAGE_JSON` 警告（不影响结果，可用 `NODE_NO_WARNINGS=1` 静音）。不要为此给 package.json 加 `type: module`，会影响 Next。
22. **别用 PowerShell 读含中文的 md / JSON**（11-10 又踩一次）：`Get-Content | ConvertFrom-Json` 会按 ANSI 解码成乱码，甚至把聊天内容整段打进会话。统计、校验一律写 node 脚本，只打印数量和布尔值。
23. **飞书粘贴按「屏幕上从左到右」的列定位，冻结列优先**（11-11 实测，T16）：`待跟进` 视图的 `客户/联系人`、`项目/现场` 两列被冻结后显示在最左，实际粘贴把第 2、3 个值放进这两列，而 lark-cli `+view-get-visible-fields` 返回的是**不含冻结**的列序（这两列在第 11、12 位）。v3、v1 两个 view 接口都不返回冻结信息（只有 `id/name/type/_meta`），字段对象也只有 `style.type`，所以**无法自动检测**。现在的处理：设置页列出将要输出的列序并提示核对；冻结列不在最左时用户要先取消冻结或换视图。另外，粘贴落在「处理人」「创建时间」这类不可写列的值会被**静默丢弃**（实测两个值消失）。11-12 复现确认：按 A 视图复制、却粘进 B 视图时，值会按 B 的屏幕顺序落位（A 的「解决方案」进了「处理状态」、「需求线索」进了「排查过程」），被挤到「处理人」「创建人」的两个值直接消失；复制提示已改成「请到「X」视图里粘贴——粘到别的视图会错位」。
24. **设置页不要用「挂载后 useEffect fetch」拿视图数据**（11-11 踩到）：接口两个都 200、时长正常，页面却一直停在「正在读取视图」。改成服务端组件直接调用 `listFeishuViews()` / `readFeishuViewColumns()` 再传 props，页面一次渲染就带数据，也不再受 React 挂载时序影响。**另**：给服务端组件新加一个 `lib/*` import 后，Turbopack dev 可能报 `Module ... was instantiated ... but the module factory is not available` 并让页面整页转圈（Fast Refresh 反复 full reload）。这不是代码问题，删掉 `workbench/.next` 再重启 `npm run dev` 即可。
25. **改完写入路径的代码，必须重启 dev server 再做任何实机验证**（11-18 事故，T31）：`lark-bitable.ts` 加了「更新前核对」后，dev server 还是 11-16 启动的旧进程，Turbopack 没加载新代码；我对真实记录 `AE-20261110-01` 调了一次「同步飞书」想验证拦截，结果旧代码照常更新了那一行（飞书历史里 18:19:47 那次），把标题/描述/解决方案/日期覆盖回本记录内容。教训：① 写入路径的验证先跑单测/集成测试，实机验证必须**重启服务并确认新代码已加载**；② 实机验证只用专门的测试记录（例如标题写「T31验证」），绝不对真实记录触发写入；③ 改完先 `npm run build` 或重启，再看 `[dev] Compiled` 日志。
26. **脚本和页面共用的 lib 代码要顺着 Node 的类型剥离写**（11-24，T26）：`scripts/*.mjs` 直接 import `src/lib/*.ts` 靠 Node 22.18+ 的类型剥离，所以 ① lib 内部相对导入必须带 `.ts` 后缀（`tsconfig.json` 为此开了 `allowImportingTsExtensions`，`noEmit` 本来就是 true，构建和类型检查都不受影响）；② 共享 lib 里**不能**出现 `import "server-only"`（纯 Node 下会直接抛），需要 `server-only` 的模块（`lark-bitable.ts`、`feishu-schema-load.ts`）不能给脚本用；③ 单元测试里 `server-only` 由 `vitest.config.ts` 的别名兜住，所以测试不会暴露这个问题，只有真跑脚本才会。
27. **回放快照必须自成一体**（11-24，T26；T32 会清理 `_t25-work/`）：`_t25-work/` 只当**导入来源**，`plan`/`apply` 把需要的截图和逐图转写按内容哈希复制进 `replay/snapshot/media|transcripts/`，详情里只存相对快照目录的路径。判断缓存有没有用，只看内容哈希，不看文件名；同一条记录里两张图内容相同只存一份（本次 541 张截图存成 537 个文件）。新记录下载的原件留在 `snapshot/_incoming/<recordId>/`，不删（规则 5），T32 一起清理。
28. **刷新快照一律「先预览、后执行」**（11-24，T26）：`plan` 只读飞书和本地，`apply` 才写盘；页面 POST 必须带 `confirm:true`，否则 400。预览和执行都只输出数量、费用、耗时，不输出客户名和飞书记录 ID（坑 11）。「飞书没被改」的证据是 `rowsFingerprint()` 的只读指纹：apply 前后各读一次表，指纹一致才算过；不一致只报告，不自动重试。
